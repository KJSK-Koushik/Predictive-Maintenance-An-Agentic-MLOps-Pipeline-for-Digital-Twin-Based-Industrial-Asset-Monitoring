# Phase 2 Acceptance Criteria

## Authorization and target safety

- [ ] The exact Supabase development/test project is owner-confirmed.
- [ ] Any activation, plan cost, region, and cloud mutation are explicitly
  approved.
- [ ] A preflight proves the target contains no unapproved production data.
- [x] Credentials exist only in ignored local files or approved secret stores.
- [x] Reports contain no project reference, private endpoint, credential, or
  signed URL.

## Storage foundation

- [ ] Raw and derived buckets exist and are private.
- [x] Bucket names are configurable and documented.
- [x] Raw object keys bind snapshot ID, SHA-256, and logical filename.
- [x] Uploads explicitly disable upsert.
- [x] Uploaded objects are downloaded and rehashed before acceptance.
- [x] Identical reruns reuse verified objects and metadata.
- [x] Different bytes at an existing key fail closed.
- [x] Concurrent same-key publication has one winner and verified reuse.
- [x] The normal raw adapter exposes no update or delete operation.
- [x] Processed and feature prefixes contain no production artifact in Phase 2.
- [x] Raw controls are described as application-enforced, not WORM.
- [x] No raw, generated, or cloud-downloaded object is tracked by Git.

## PostgreSQL migrations and security

- [x] Migration filenames are generated by the pinned Supabase CLI.
- [x] Migrations apply from a clean PostgreSQL 17 database.
- [x] A clean reset/reapply produces the same schema.
- [x] The private `ops` schema contains only the approved Phase 2 tables.
- [x] Primary, foreign, unique, state, hash, size, and timestamp constraints are
  exercised.
- [x] `PUBLIC`, `anon`, and `authenticated` cannot access operational objects.
- [x] The runtime role has only the required table and sequence privileges.
- [x] RLS and grants are tested independently where RLS is used.
- [x] No custom table or function is created in `auth`, `storage`, or
  `realtime`.
- [x] The `ops` schema is not exposed through the Data API.
- [ ] Migration history matches the repository.

## Idempotency, lineage, and recovery

- [x] Phase 1 `snapshot_id` is the publication idempotency identity.
- [x] One accepted snapshot links to every required raw object.
- [x] Lineage rejects missing parents, self-links, and duplicate edges.
- [x] Metadata becomes available only after all objects pass verification.
- [x] A storage-success/database-failure retry converges without duplicate
  metadata or overwrite.
- [x] Missing, mismatched, orphaned, and metadata-only objects are reported by
  reconciliation.
- [x] Inconsistent state blocks downstream use and is not silently repaired.
- [x] Error records use stable codes and sanitized bounded details.
- [ ] The approved database and object backup procedure is documented.
- [x] At least one test metadata/object recovery exercise passes.

## Local and cloud evidence

- [x] Unit, contract, migration, security, failure, and local integration tests
  pass.
- [x] Docker Compose PostgreSQL startup, health, migration, and cleanup pass.
- [x] Filesystem and Supabase adapters pass the same core object contract.
- [x] The actual owner-provided FD001 snapshot passes local publication logic.
- [ ] A real approved Supabase project passes bucket, upload, download,
  overwrite-denial, database, lineage, idempotency, and reconciliation checks.
- [x] Fixture, local substitute, and cloud evidence are reported separately.
- [ ] Supabase Security and Performance Advisors are recorded and all
  introduced critical/high findings are resolved.

## Engineering and CI evidence

- [x] Core publication logic remains typed and independent of vendor SDK types.
- [x] Product source maintains at least 90% branch-aware coverage.
- [ ] Formatting, linting, strict typing, Markdown, YAML, lock, dependency,
  migration, secret, and security checks pass.
- [x] Pull-request CI remains least-privilege and contains no cloud credential,
  deployment, or production mutation.
- [ ] The required GitHub Actions workflow passes on the Phase 2 commit.
- [ ] Required branch protection is verified for the current quality context.
- [ ] No critical or high-severity issue remains unresolved.

## Documentation and completion

- [x] `docs/DATA_CONTRACT.md` records cloud object and metadata identity.
- [x] Master and phase architecture match exercised behavior.
- [x] Storage, migration, security, backup, and partial-failure decisions are
  recorded in ADRs.
- [x] Manual prerequisites and exact evidence commands are updated.
- [ ] `COMPLETION_REPORT.md` records local, Docker, cloud, advisor, backup, CI,
  limitation, and severity evidence.
- [ ] `docs/PROJECT_STATUS.md` is updated to `AWAITING_APPROVAL`.
- [ ] The completion handoff asks for `APPROVE PHASE 2`.

Unchecked criteria prevent Phase 2 completion.
