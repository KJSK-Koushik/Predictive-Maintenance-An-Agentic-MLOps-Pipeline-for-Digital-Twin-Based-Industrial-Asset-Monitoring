# Phase 2 Acceptance Criteria

## Authorization and target safety

- [ ] The exact Supabase development/test project is owner-confirmed.
- [ ] Any activation, plan cost, region, and cloud mutation are explicitly
  approved.
- [ ] A preflight proves the target contains no unapproved production data.
- [ ] Credentials exist only in ignored local files or approved secret stores.
- [ ] Reports contain no project reference, private endpoint, credential, or
  signed URL.

## Storage foundation

- [ ] Raw and derived buckets exist and are private.
- [ ] Bucket names are configurable and documented.
- [ ] Raw object keys bind snapshot ID, SHA-256, and logical filename.
- [ ] Uploads explicitly disable upsert.
- [ ] Uploaded objects are downloaded and rehashed before acceptance.
- [ ] Identical reruns reuse verified objects and metadata.
- [ ] Different bytes at an existing key fail closed.
- [ ] Concurrent same-key publication has one winner and verified reuse.
- [ ] The normal raw adapter exposes no update or delete operation.
- [ ] Processed and feature prefixes contain no production artifact in Phase 2.
- [ ] Raw controls are described as application-enforced, not WORM.
- [ ] No raw, generated, or cloud-downloaded object is tracked by Git.

## PostgreSQL migrations and security

- [ ] Migration filenames are generated by the pinned Supabase CLI.
- [ ] Migrations apply from a clean PostgreSQL 17 database.
- [ ] A clean reset/reapply produces the same schema.
- [ ] The private `ops` schema contains only the approved Phase 2 tables.
- [ ] Primary, foreign, unique, state, hash, size, and timestamp constraints are
  exercised.
- [ ] `PUBLIC`, `anon`, and `authenticated` cannot access operational objects.
- [ ] The runtime role has only the required table and sequence privileges.
- [ ] RLS and grants are tested independently where RLS is used.
- [ ] No custom table or function is created in `auth`, `storage`, or
  `realtime`.
- [ ] The `ops` schema is not exposed through the Data API.
- [ ] Migration history matches the repository.

## Idempotency, lineage, and recovery

- [ ] Phase 1 `snapshot_id` is the publication idempotency identity.
- [ ] One accepted snapshot links to every required raw object.
- [ ] Lineage rejects missing parents, self-links, and duplicate edges.
- [ ] Metadata becomes available only after all objects pass verification.
- [ ] A storage-success/database-failure retry converges without duplicate
  metadata or overwrite.
- [ ] Missing, mismatched, orphaned, and metadata-only objects are reported by
  reconciliation.
- [ ] Inconsistent state blocks downstream use and is not silently repaired.
- [ ] Error records use stable codes and sanitized bounded details.
- [ ] The approved database and object backup procedure is documented.
- [ ] At least one test metadata/object recovery exercise passes.

## Local and cloud evidence

- [ ] Unit, contract, migration, security, failure, and local integration tests
  pass.
- [ ] Docker Compose PostgreSQL startup, health, migration, and cleanup pass.
- [ ] Filesystem and Supabase adapters pass the same core object contract.
- [ ] The actual owner-provided FD001 snapshot passes local publication logic.
- [ ] A real approved Supabase project passes bucket, upload, download,
  overwrite-denial, database, lineage, idempotency, and reconciliation checks.
- [ ] Fixture, local substitute, and cloud evidence are reported separately.
- [ ] Supabase Security and Performance Advisors are recorded and all
  introduced critical/high findings are resolved.

## Engineering and CI evidence

- [ ] Core publication logic remains typed and independent of vendor SDK types.
- [ ] Product source maintains at least 90% branch-aware coverage.
- [ ] Formatting, linting, strict typing, Markdown, YAML, lock, dependency,
  migration, secret, and security checks pass.
- [ ] Pull-request CI remains least-privilege and contains no cloud credential,
  deployment, or production mutation.
- [ ] The required GitHub Actions workflow passes on the Phase 2 commit.
- [ ] Required branch protection is verified for the current quality context.
- [ ] No critical or high-severity issue remains unresolved.

## Documentation and completion

- [ ] `docs/DATA_CONTRACT.md` records cloud object and metadata identity.
- [ ] Master and phase architecture match exercised behavior.
- [ ] Storage, migration, security, backup, and partial-failure decisions are
  recorded in ADRs.
- [ ] Manual prerequisites and exact evidence commands are updated.
- [ ] `COMPLETION_REPORT.md` records local, Docker, cloud, advisor, backup, CI,
  limitation, and severity evidence.
- [ ] `docs/PROJECT_STATUS.md` is updated to `AWAITING_APPROVAL`.
- [ ] The completion handoff asks for `APPROVE PHASE 2`.

Unchecked criteria prevent Phase 2 completion.
